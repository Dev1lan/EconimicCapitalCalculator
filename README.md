# CF-калькулятор IRRBB: расчётное ядро `cfcore`

Ядро на C++20 строит договорные денежные потоки по сделкам и раскладывает их по 19 временным интервалам (бакетам) 8-МР. Это часть 1 проекта «факторный анализ изменения Economic Capital». Кривые и дисконт-факторы делает другая команда, их умножение на потоки и расчёт рисков будут добавлены позже.

**Статус:** работающий MVP. Сделка 1 совпадает с Excel куратора по всем 334 строкам. По RGM, SIMPLE и плавающим ставкам эталона нет: они считаются по допущениям команды, перечисленным в разделе 7.

## 2. Как запустить

Нужны CMake 3.20+, компилятор с C++20 и Python 3. GoogleTest берётся из системы, а если его нет, скачивается при сборке. Внешних библиотек ядру не требуется.

### Простой запуск: команда `./cf`

Посчитать нормализованный файл (формат в разделе 4). Команда запускается из корня репозитория и сама собирает ядро, если нужно:

```bash
./cf file out/synthetic/deals.csv
```

В папке `out/cli/file_<имя файла>/` появятся `cashflows.csv` и `deal_summary.csv`. На экран выводятся пути к ним и время расчёта. Если часть сделок не посчитана, появится строка с их числом по кодам ошибок.

Только `deal_summary.csv`, без записи потоков:

```bash
./cf file out/synthetic/deals.csv --summary-only
```

### Запуск вручную

Всё сразу (сборка, тесты, 55 сделок, синтетика):

```bash
python3 -m pip install -e ./cf-normalizer
bash tools/demo.sh 10000
```

Если нужен другой интерпретатор Python, задайте его через `PYTHON=/path/to/python`.

Только сборка и тесты:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build -j8 && ctest --test-dir build
```

Сборка с проверками памяти:

```bash
cmake -S . -B build-asan -DCMAKE_BUILD_TYPE=Debug -DCFCORE_SANITIZE=ON && cmake --build build-asan -j8 && ctest --test-dir build-asan
```

Тестовые сделки МАИ через штатный нормализатор:

```bash
python3 -m normalizer data/input/test_deals_mai.csv --output-dir out/mai --format csv \
  --cfcore build/core/cfcore --fixings data/input/key_rate.csv
python3 tools/verify_output.py out/mai/core
```

Ручной расчёт и команды для Windows описаны в [инструкции сквозного запуска](docs/cf-integration.md).

Синтетический портфель. Один `seed` всегда даёт один и тот же файл, `--bad-share` намеренно портит долю сделок:

```bash
python3 tools/gen_synthetic.py out/synthetic/deals.csv --deals 100000 --seed 42 --bad-share 0.001
```

```bash
./build/core/cfcore --input out/synthetic/deals.csv --output-dir out/synthetic/run
```

Опции `cfcore`:

| Опция | Смысл |
|---|---|
| `--input FILE` | Нормализованный CSV сделок, обязательно |
| `--output-dir DIR` | Папка для результатов, обязательно |
| `--fixings FILE` | История индикатора, колонки `date,value` |
| `--threads N` | Число потоков, по умолчанию все ядра |
| `--excel-etalon` | Правила листа «1 сделка» |
| `--no-flows` | Не писать `cashflows.csv`, нужно на больших портфелях |
| `--events` | Записать пересмотры ставок по портфелю в `events.csv` |
| `--trace-deal ID` | Записать детализацию расчёта для одного `instrument_id` в `deal_trace.csv` |
| `--details-only` | Не писать `buckets.csv`, `errors.csv` и манифест, без сводки на экране. Вместе с `--no-flows` остаётся `deal_summary.csv` и явно запрошенные отчёты событий |
| `--round-money` | Округлить суммы до копеек при выводе |

### Пересмотры ставок и детализация сделки

```bash
./build/core/cfcore --input out/mai/deals.csv --output-dir out/mai/run \
  --fixings data/input/key_rate.csv --events --trace-deal 44
```

На Windows запускайте собранный `cfcore.exe`. Входной файл, история ставок и каталог вывода могут иметь имена с кириллицей. Поле `input` манифеста хранит исходный путь как строку JSON.

`events.csv` содержит строки `REPRICING` с датой, действующими ставками до и после пересмотра, источником и `cash_amount=0`. Источники — договорный график (`CONTRACT_SCHEDULE`), ставка договора (`CONTRACT_RATE`), история индикатора (`FIXING_HISTORY`) или индикатор во входных данных сделки (`DEAL_INDICATOR`). Отчёт включает пересмотры, обработанные расчётным циклом, в том числе без изменения итоговой ставки.

В `deal_trace.csv` каждая строка показывает интервал начисления, фактические дни, долю года, остатки до и после события, начисление и выплаты. `rate_before` действует на указанном интервале. В строке пересмотра `rate_after` применяется к следующему интервалу. Для запланированных событий одной даты порядок такой: проценты, тело, пересмотр. Доначисленные проценты, которые ядро выплачивает после последнего события, показаны отдельной строкой. Если между двумя выплатами было несколько ставок, начисления по всем строкам периода образуют сумму купона. Диагностические значения выводятся с исходной точностью.

Оба отчёта можно включать независимо и вместе с `--no-flows`. При отсутствующей или отклонённой сделке `deal_trace.csv` содержит заголовок. `cashflows.csv` сохраняет прежние колонки. Его `rate_used` показывает ставку на момент выплаты, а разбивку купона по ставкам даёт `deal_trace.csv`.

## 3. Как устроено ядро

### Конвейер

```text
CSV банка → нормализатор (Python) → нормализованный CSV → cfcore → cashflows.csv
                                                                 → buckets.csv ──× дисконт-факторы (другая команда, позже)
                                                                 → deal_summary.csv, errors.csv, run_manifest.json
```

Данные идут в одну сторону: входной файл не меняется, результат пишется в отдельные файлы. Ядро читает файл порциями по 100 000 сделок, считает порцию и берёт следующую. Поэтому память не зависит от размера файла, кроме `buckets`, где хранятся только векторы по ключам.

### Путь одной сделки

```text
validate → build_events → settle → проверка конечности чисел → aggregate
```

1. **`validate`** проверяет числа, даты, правила и списки. При ошибке сделка пропускается и попадает в `errors.csv`.
2. **`build_events`** превращает условия договора в упорядоченный список событий: выплата процентов, погашение долга, пересмотр ставки.
3. **`settle`** проходит по событиям и получает потоки. Этот цикл один на все типы сделок.
4. Сделка записывается в результат **целиком или никак**: если появился `NaN`, её потоки откатываются и бакеты не портятся.
5. **`aggregate`** раскладывает потоки по бакетам и складывает по ключу «портфель, валюта, сторона».

### Параллельность и воспроизводимость

Сделки делятся на блоки по 1024 штуки, потоки разбирают блоки по очереди, а результаты сливаются строго по номеру блока. Поэтому порядок сложения не зависит от числа потоков: файлы результата при 1, 2 и 16 потоках совпадают по контрольной сумме.

Суммы накапливаются по алгоритму Ньюмана, чтобы мелкие платежи не терялись рядом с большими суммами. Сборка использует `-ffp-contract=off`, а при `-ffast-math` компиляция останавливается: такой флаг ломает компенсацию.

### Вход: нормализованный CSV

Разделитель `;`, даты ISO (`2022-08-31`), ставки как доли (`0.075`), пусто означает «значения нет». Список колонок: [`tools/normalized_format.py`](tools/normalized_format.py). Отличия от исходного файла банка:

| Колонка | Формат |

## 5. Формулы

Метки источника:

- **[Excel]** подтверждено листом «1 сделка» куратора;
- **[8-МР]** прямо следует из методики;
- **[Куратор]** ответ куратора в переписке;
- **[Допущение]** решение команды без подтверждения.

Обозначения: `B` — остаток основного долга на дату отчёта, `r` — годовая ставка (доля), `d` — дата события, `p` — начало периода начисления, `N` — число платежей, `i = r/12`.

### 5.1 Даты

Дата хранится как число дней от 1970-01-01, это тот же формат, что `date32` в Arrow.

**Сдвиг на месяцы с обрезкой по концу месяца:**

```text
t  = год·12 + (месяц − 1) + n
год' = ⌊t / 12⌋,  месяц' = (t mod 12) + 1
день' = min(день, дней_в_месяце(год', месяц'))
```

Платёжные даты считаются **от начальной даты правила**, а не от предыдущего платежа, поэтому 31-е число не «съезжает» на 28-е навсегда. **[Допущение]**, в Excel день 22-й и разницы нет.

### 5.2 Доля года τ(p, d)

**ACT/365** **[Excel]**:

```text
τ(p, d) = (d − p) / 365
```

**ACT/ACT ISDA** (период делится по границам календарных лет):

```text
τ(p, d) = Σ по годам Y: (дней периода в году Y) / (366, если Y високосный, иначе 365)
```

В Excel проценты считаются по /365 даже при конвенции ACT/ACT. В базовом режиме ядро использует конвенцию сделки, режим Excel включает `force_act365`. Код `ACT/ACT` без `ISDA` трактуется как ISDA **[Допущение]**.

### 5.3 Платёжные даты регулярного графика

```text
d_k = add_months(start, k·P, D)         для периода в месяцах
d_k = start + k·P                       для периода в днях
prev = последняя дата графика не позже даты отчёта
```

`D` — день месяца из правила или день начальной даты. Будущие даты идут, пока `d_k < maturity`, затем ставится платёж на `maturity` **[Excel]**. Период `ENDDATE` даёт один платёж на дату погашения.

Откуда берутся даты:

| Что | Источник по порядку |
|---|---|
| Проценты | Явный список → правило процентов → регулярное правило → дата погашения |
| Долг ANN, RGM | Регулярное правило → правило процентов → дата погашения |
| Долг SIMPLE | Явный список → разовое погашение на дату погашения **[Допущение]** |

У ANN проценты и долг выплачиваются в одни даты: один платёж содержит обе части. Платежи с датой не позже отчёта пропускаются: остаток на дату отчёта их уже учитывает **[Допущение]**.

### 5.4 Ставка

Фиксированная сделка:

```text
r = ставка договора
```

Плавающая сделка **[Куратор]** для правила «последнее известное значение»:

```text
индикатор(d) = последнее значение КС не позже min(d, дата отчёта)
r = индикатор(d) + interest_rate             [Допущение: interest_rate — надбавка]
```

Смысл: на будущие платежи действует КС, известная на дату отчёта. Прогноз и форварды не используются. Ограничения cap и floor берутся из данных сделки и применяются ко всем сделкам **[Допущение]**:

```text
r_итог = min( max(r, floor), cap )
```

Если значения индикатора нет, сделка получает ошибку `MISSING_RATE`. Ноль никогда не подставляется.

Если в графике есть договорная ставка на дату пересмотра, она заменяет `interest_rate`, начиная с этой даты.

### 5.5 Общий расчётный цикл

События сортируются по дате. На одной дате порядок такой: проценты, погашение, смена ставки. Проценты считаются по остатку **до** погашения.

```text
баланс = B;  p = начало начисления;  начислено = 0

для каждого события на дату d:
    начислено += баланс · r · τ(p, d)
    p = d
    Проценты:   выплатить «начислено», обнулить
    Погашение:  сумма = min(max(сумма, 0), баланс);  баланс −= сумма
    Пересмотр:  r = новая ставка
```

Начисление идёт на **каждом** событии, поэтому если долг частично погашен между процентными датами, проценты разделятся на участки с разным остатком:

```text
проценты = B₁·r·τ(p, x) + B₂·r·τ(x, d)
```

На сделке 1 это совпадает с Excel, потому что даты долга и процентов одинаковы. Для SIMPLE это наше уточнение **[Допущение]** по сравнению с `interest = B·r·τ` на весь период.

Начало начисления: предыдущая платёжная дата **[Excel]**. Если прошлых дат нет, начало сделки **[Допущение]**.

Проценты, начисленные после последней процентной даты, выплачиваются вместе с последним событием **[Допущение]**.

### 5.6 ANN — аннуитет

```text
pmt = B · i / (1 − (1 + i)^(−N))              [Excel]
pmt = B / N                                    при r = 0
```

В коде знаменатель считается как `−expm1(−N · log1p(i))`. Это та же величина, но без потери точности при малых ставках: при `r = 1e-12` классическая запись ошибается на 8,10 руб., а эта — на 1e-13 руб. Для сделки 1 платёж остаётся 26 037,32199992.

На каждой дате:

```text
проценты = остаток · r · τ(p, d)
долг     = pmt − проценты, в пределах [0, остаток]
```

Нижняя граница нужна, если проценты длинного первого периода больше платежа **[Допущение]**.

Последний платёж:

- базовый режим: долг равен всему остатку, сделка гасится в ноль (инвариант лида);
- режим Excel: остаток не гасится, у сделки 1 остаётся 15 420,45 руб. **[Excel]**.

Остаток появляется потому, что `pmt` считается по `r/12`, а проценты — по фактическим дням. Если ставка меняется, `pmt` пересчитывается на оставшиеся платежи **[Допущение]**. ANN поддержан только с ежемесячным графиком.

### 5.7 RGM — равные части долга [Допущение]

```text
долг_j = B / N
проценты_j = остаток · r · τ(d_(j−1), d_j)
```

Последний платёж закрывает остаток.

### 5.8 SIMPLE — явный график [Допущение]

Суммы долга берутся из списка, проценты начисляются циклом из раздела 5.5. Прошлые элементы списка пропускаются. Сумма будущих элементов сверяется с остатком с допуском 0,01 руб. на платёж, потому что суммы в данных округлены до копеек (у сделки 44 разница 0,01):

```text
Σ суммы > B + допуск  →  SCHEDULE_SUM_MISMATCH
Σ суммы < B − допуск  →  SCHEDULE_ENDS_EARLY
```

### 5.9 Current interest [Допущение, трактовка лида]

`current_interest` — начисленные, но не выплаченные проценты на дату отчёта, поле `accrued_interest`.

```text
если значение есть (в том числе 0)  →  берём его, источник REPORTED
иначе если данных достаточно        →  B · r · τ(последняя процентная дата, дата отчёта), COMPUTED
иначе                               →  пусто, UNAVAILABLE
```

В первый купон **не прибавляется**: купон уже рассчитан за полный период, иначе проценты учитывались бы дважды. Значение выводится в `deal_summary.csv`.

upper_k = add_months(дата отчёта, M_k)

### 5.11 Суммирование (алгоритм Ньюмана)

```text
t = sum + x
если |sum| ≥ |x|:  c += (sum − t) + x
иначе:             c += (x − t) + sum
sum = t
результат = sum + c
```

Пример из тестов: 1e16 плюс миллион единиц минус 1e16 даёт ровно 1 000 000, а обычное сложение даёт 0.

### 5.12 Следующие слои (в ядро не входят, для понимания)

**Дисконтирование и изменение стоимости.** Здесь есть расхождение, которое надо закрыть при интеграции:

| | Формула | Сделка 1, NPV база | dNPV |
|---|---|---|---|
| Excel | `DF_k = (1 + r_k)^(−T_k)` | 2 056 999,50 | −164 522,41 |
| 8-МР, п. 4.2.1 | `DF_k = e^(−r_k·T_k)` | 1 921 403,83 | −159 753,70 |

Обе строки посчитаны при одних и тех же ставках. Эталоном принята 8-МР, но её формула относится к непрерывной ставке: кривая должна быть передана в согласованной конвенции, поэтому способ начисления обязательно нужно закрепить с командой кривых. Ядро от этого не зависит: `NPV = Σ_k (долг_k + проценты_k) · DF_k`.

Знак: в Excel `dNPV = стресс − база`, в 8-МР (п. 4.2.2) `ΔЭСК = база − стресс + ИСО`.

**Досрочное погашение (п. 2.4.2.2 8-МР).** Считается по портфелю однородных кредитов поверх бакетов, поэтому ядро менять не нужно:

```text
РВДПК(сц) = min(1, коэф_сц · БВДПК)
ДП(ви)    = КДП(ви) + РВДПК(сц) · УЗ(ви−1) · ДИ(ви)/30
УЗ(0)     = ВПОК
УЗ(ви)    = max(УЗ(ви−1) − КДПОД(ви) − РВДПК(сц) · УЗ(ви−1) · ДИ(ви)/30; 0)
```

В данных есть только код модели (`behavior_model_cd`). БВДПК — среднее за два года по статистике банка, этих значений у нас нет.

## 6. Как проверяется точность

CTest запускает модульные и эталонные проверки C++. При наличии Python также проверяется CLI. Сквозные Python-тесты запускаются отдельно.

| Проверка | Что подтверждает |
|---|---|
| Золотой тест, режим Excel | Даты, долг, проценты, остаток и бакет всех 334 строк листа «1 сделка», допуск 1e-6 |
| NPV через дисконт-факторы листа | База 2 056 999,4971 и стресс 1 892 477,0845, допуск 1e-6. DF только в тесте, ядро их не использует |
| Базовый режим на сделке 1 | Те же даты, долг погашен полностью |
| Даты | Каждый день 1900–2200 туда-обратно, 5 000 дат против Python `datetime`, 5 000 сдвигов против `relativedelta` |
| Ручные примеры | Bullet, погашение между процентными датами, сплит ставки при пересмотре |
| Числа потоков 1, 2, 16 | Точное совпадение сумм, совпадение файлов по контрольной сумме |
| Инварианты в `tools/verify_output.py` | Долг погашен, нет отрицательных сумм, бакеты равны сумме потоков, счётчики сходятся |
| Плохие данные | `NaN`, бесконечность, неверные даты, неизвестные коды изолируются и не портят бакеты |

**Что это не доказывает.** Совпадение с эталоном подтверждено только для сделки 1 (ANN, FIXED). Для RGM, SIMPLE и FLOAT проверяются внутренняя согласованность и инварианты, а не правильность методики.
